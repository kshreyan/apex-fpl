# APEX FPL Research Plan

**Date:** 2026-08-14. This document sequences Phases 0-12 from the master spec into concrete, falsifiable milestones. It is a living plan — update it in place as phases close, don't create parallel copies.

## Phase 0 — Repository and research audit (this session)
Deliverables: `docs/world_cup_transfer_audit.md`, `docs/fpl_gap_analysis.md`, this file, `configs/seasons/2026_27.yaml`, repo scaffold. **Exit criterion:** every claim in the transfer audit is traceable to a specific file/line read, not inferred.

## Phase 1 — Rules and data
Build canonical entities (players, clubs, fixtures, gameweeks) from the FPL API, with Bronze (immutable snapshots) / Silver (canonical tables) / Gold (deadline-snapshotted features) layers. Start capturing weekly `bootstrap-static` + `fixtures` snapshots **immediately**, regardless of how much historical backfill is achievable — every week this doesn't happen is prospective evaluation data that can never be recovered. Resolve the three blockers flagged in the gap analysis (event-data source, odds feed, Vaastav archive audit) enough to know what Phase 1 can and can't cover. **Exit criterion:** `tests/leakage/` passes against at least one fully reconstructed historical gameweek snapshot.

## Phase 2 — Baseline end-to-end system — DONE 2026-08-14
The simplest honest pipeline: ported/refit team-goal model → naive minutes model (recent start-rate) → proportional player-event allocation → deterministic scoring engine → Monte Carlo → smallest legal optimizer (single-gameweek squad selection under budget/quota constraints, no transfers/chips yet). Run on one real historical gameweek (2022-23 season, GW20 — chosen as grade-A audited and pre-defensive-contributions). Full report: `docs/phase2_milestone_report.md`. Frozen artifact + evaluation: `artifacts/phase2_milestone/`. Result: model squad realized 81 points vs a recent-form baseline's 50 — **explicitly not treated as validated forecasting skill, n=1 gameweek is not statistical evidence**; the milestone's actual purpose (proving the pipeline runs end-to-end on real data with a frozen, falsifiable, scoreable output) is met. Two real bugs were found and fixed by the tests written alongside this work (a YAML structural error in the rules config; a clean-sheet minutes-gating mismatch between the simulator's vectorized fast path and the authoritative scoring engine).

## Phase 3 — Historical replay framework — DONE 2026-08-14
Generalized Phase 2 into deadline-by-deadline sequential replay across GW7-38 of the 2022-23 season (GW7 is a genuine blank gameweek, correctly detected and skipped — see report). Full writeup: `docs/phase3_replay_report.md`. Reusable core extracted into `src/apex_fpl/backtesting/replay.py` (now shared by both the Phase 2 single-GW script and the Phase 3 loop). Added the strongest leakage test in the project so far (`tests/leakage/test_replay_no_future_leakage.py`): truncating all future data byte-for-byte and confirming the recommendation is IDENTICAL, not just plausible.

**Key finding, reported without spin:** across 31 real gameweeks, the model-driven squad and a naive recent-form baseline tied exactly on total points (1,667 each), mean per-GW difference +0.00 with a 95% bootstrap CI of [-5.07, +5.23] — no detectable edge. This directly confirms the Phase 2 report's own warning that its single-gameweek +31 result was not evidence of skill. This is the correct and expected state for an unrefit Phase 2 baseline (team-model constants ported unmodified from international football, proportional attacking allocation, no DC/BPS) — it is a clean starting point for Phase 4's model tournaments to actually try to beat, not a failure of the research process.

## Phase 4 — Model tournaments — team model DONE 2026-08-15, others not started
Ran the first real model tournament: team-goal forecasting, nested temporal CV across 6 seasons (2019-20..2024-25), 3 outer folds, champion (unfit constants) vs challenger (grid-tuned constants) vs 2 mandatory baselines. Full report: `docs/phase4_tournament_report.md`. Result registry: `artifacts/model_registry.json`.

**Findings:** (1) the ported attack/defense mechanism clearly beats both naive baselines on every proper scoring rule, across all 3 outer folds — the core mechanism is validated, not just added complexity. (2) Phase 3's hypothesis that refitting the unfit constants would be "the most likely source of a genuine improvement" was **tested and not confirmed** — block-bootstrapped log-loss difference +0.0008, 95% CI [-0.0049, +0.0066], not promoted. This redirects the next round of work: the team model is not the bottleneck behind Phase 3's flat FPL-points result; the minutes model and (especially) the proportional attacking-allocation baseline are the more likely culprits and are next.

**Update 2026-08-15 — minutes and attacking model tournaments DONE:** `docs/phase4b_tournament_report.md`. Both champions were replaced with strong statistical backing (minutes: exponential-recency-decay, log-loss diff -0.537 95% CI [-0.594,-0.479]; attacking: Dirichlet shrinkage, Poisson-NLL diff -0.275 95% CI [-0.295,-0.255]; both on 48,575 real observations). Wired into `src/apex_fpl/backtesting/replay.py` as the new production defaults. **Closing-the-loop check:** re-ran Phase 3's season replay with both promotions active — directionally positive across 2 seasons (2022-23 and 2023-24, model beat baseline in both), but the pooled 63-gameweek decision-level bootstrap CI [-1.30, +5.78] still spans zero and a sign test lands at p=0.062 — not significant by this project's own pre-registered bar. Reported exactly as measured: strong, real component-level wins that have not yet been *confirmed* (though they are consistent with) a season-level FPL-points improvement — this is expected given ~31 gameweeks/season is a much lower-powered test than ~48,575 player-gameweek observations, not a contradiction.

**Update 2026-08-15 — decision-level significance CONFIRMED:** `docs/phase3_extended_replay_report.md`. Extended the closing-the-loop replay from 2 to 4 genuinely independent seasons (2020-21, 2022-23, 2023-24, 2024-25 — 2021-22 excluded as the Phase 4b tuning season, 2019-20 excluded for an incompatible older data schema, both documented reasons). Pooled 127-gameweek bootstrap CI **[+0.85, +5.27] excludes zero** — the Phase 4b promotions are now confirmed to significantly improve realized FPL points, not just component-level metrics (sign test p=0.0024 corroborates). Two more real bugs found and fixed while extending: 2019-20's non-contiguous gameweek numbering (COVID restart renumbering, fixed via `vaastav_loader.season_gameweeks()`), and 2024-25's new "Manager" pseudo-player mechanic crashing position lookups (fixed by filtering to classic squad positions).

Remaining for Phase 4: market models (blocked on an odds feed, per `docs/data_sources.md`); a dedicated attacking-lookback grid search (Phase 4b shared a hyperparameter with the minutes tuning for tractability, flagged as a limitation); 2019-20 support (needs joining merged_gw rows through element IDs against players_raw.csv/teams.csv for that season's older schema).

## Phase 5 — Calibration and uncertainty — DONE 2026-08-15
Full report: `docs/phase5_calibration_report.md`. Built a binary calibrator (`src/apex_fpl/calibration/calibrator.py`, isotonic + Platt via scikit-learn, method selected by fitting-set log loss) and applied it to two real champion outputs with proper calibration-fit/test season separation (fit on 2020-21, test on 2022-23/2023-24/2024-25, block-bootstrap significance test).

**Findings:** (1) minutes P(60+) calibration is a massive, highly significant win — log loss 0.7277→0.3072, 95% CI on the improvement [-0.4913,-0.3860], caused by the promoted exponential-decay model being severely overconfident (54% of predictions cluster in [0,0.1] with a 4.4x understated true rate). (2) Clean-sheet probability calibration was correctly REJECTED — the raw team-model output was already excellently calibrated (slope 1.001), and isotonic regression on a small 644-observation fitting set overfit and made it worse (CI [+0.0178,+0.0966], harmful); the held-out promotion gate caught this correctly, though `fit_calibrator`'s method-selection step (choosing isotonic/Platt by fitting-set log loss) is flagged as a known bias-toward-isotonic weakness worth fixing later. (3) Built uncertainty decomposition (`src/apex_fpl/simulation/uncertainty.py`, law of total variance on real Monte Carlo samples, split into selection/minutes vs aleatoric) — confirms the same overconfidence concretely: several nailed-on players show literal 0% selection uncertainty in the simulator, the live-simulation manifestation of finding (1). Also added model-disagreement reporting from Phase 4a's two evaluated team models as a grounded model-uncertainty signal. Role/data/schedule uncertainty (also named in spec Part XVIII) are explicitly NOT computed — no evidence-backed way to yet, tracked as open gaps rather than faked.

**Update 2026-08-15 — wired into production, decision-level effect honestly inconclusive:** `docs/phase5_production_wiring_report.md`. `src/apex_fpl/calibration/production_calibrators.py` fits and caches the validated minutes-P(60+) calibrator once (on 2020-21, never refit per-call); `replay.run_gameweek()` applies it by default with a defensive clamp preserving P(60+) ≤ P(appearance). Re-ran the Phase 3 decision-level replay across all 4 independent seasons: pooled result remains significant (CI [+1.09,+5.42], sign test p=0.0157), but calibration's *specific* incremental contribution over the Phase 4b baseline is small and NOT distinguishable from zero (season-level paired delta +0.195/GW, CI [-0.52,+0.98] — only 4 data points, a real evidentiary limit, honestly reported as such). Kept wired in anyway: independently justified by its own strong component-level evidence and as groundwork for future uncertainty-sensitive decisions (captaincy risk, robust optimization, rank simulation), not because the decision-level increment was confirmed. A process gap was also flagged: pre-calibration per-gameweek artifacts were overwritten by the rerun rather than preserved, which prevented the fine-grained per-GW bootstrap this comparison should have had.

## Phase 6 — Joint simulation — DONE 2026-08-15 (built and evaluated, not promoted)
Full report: `docs/phase6_joint_simulation_report.md`. Built a reduced-form per-position BPS regression (`src/apex_fpl/models/bonus/bps_model.py`, fit on real 2022-23 events, validated on held-out 2023-24: R² 0.81-0.93, MAE 1.9-3.4) and a joint simulator (`src/apex_fpl/simulation/joint_simulator.py`) that allocates each scenario's team goal total multinomially across scorers/assisters (`sum(player_goals) == team_goals` by construction, verified directly) and ranks bonus points within each match using the official tie-break rule (verified against premierleague.com, not assumed from memory).

**Findings, reported without spin:** the naive top-line comparison (per-player expected-points MAE with vs without bonus, 2022-23 GW20, n=699) looks like a regression — 0.979 → 1.043 — but that's an artifact of the metric: 666/699 players won zero bonus, and any nonzero bonus prediction can only add error for them. Splitting by actual outcome reveals the real signal: for the 33 players who genuinely won bonus, joint simulation is *more* accurate (MAE 7.003 → 6.774), while for non-winners it's slightly worse (0.681 → 0.759) — a real, if weak (correlation 0.249), positive effect concentrated exactly where it should be, masked by aggregating over a population dominated by trivial zero-cases. Even so, the model badly under-predicts bonus *magnitude* for real winners (simulated mean 0.01-0.88 vs actual 3) — plausibly because the reduced-form features can't see the defensive/creative-action volume that real BPS partly depends on, the same event-data gap that motivated the reduced-form approach to begin with.

**Decision: NOT PROMOTED**, correctly scoped as build-and-validate work rather than a production change. The joint-simulation *machinery* (reconciliation, tie-break-correct ranking) is verified correct independent of any one gameweek's outcome and is a real capability gain over the baseline (which never simulated bonus at all); the *prediction quality* is a genuine, measured limitation. A real bug was found and fixed while testing: non-participants could receive a bonus point in small matches because the ranking function didn't exclude them before computing rank position — caught by a dedicated test before it ever reached real data.

**Update 2026-08-15 — multi-gameweek validation CONFIRMS both findings, closing the question:** `docs/phase6_joint_simulation_report.md`'s addendum. Re-ran across 31 real gameweeks spanning the same 4 independent seasons used throughout this project, with the BPS model refit strictly walk-forward on 2021-22 only (resolving the earlier leakage caveat — it barely moved the held-out metrics). Block-bootstrapped across all 31 gameweeks: all-players MAE diff +0.071 95% CI [+0.067,+0.076] (aggregate degradation confirmed real), bonus-winners MAE diff -0.229 95% CI [-0.241,-0.216] (bonus-winner-specific improvement also confirmed real), both with the same sign in every one of 31/31 gameweeks tested — not a lucky single-gameweek draw in either direction. The blanket-replacement question is now closed (decisively not promoted), while the underlying signal is confirmed genuine but small, pointing toward a more surgical future application rather than more data collection on the same test.

## Phase 7 — Multiweek optimizer — DONE 2026-08-15 (built and validated on one season, not yet wired to production)
Full report: `docs/phase7_multiweek_optimizer_report.md`. Built `src/apex_fpl/optimization/transfers.py`: an exact MILP jointly choosing squad membership, starting XI, captain, AND transfers across a forecast horizon, correctly modeling 2026/27's confirmed free-transfer banking (1/gw, cap 5) and -4 hit costs via a linear "sandwich" relaxation that's provably exact at the optimum. `rolling_horizon_transfers()` is the receding-horizon driver (re-solve every real gameweek, commit only that gameweek, re-solve fresh next week) — `horizon=1` gives a myopic policy and `horizon>1` gives genuine lookahead through the SAME code path, so the two are a true apples-to-apples comparison. This is the real structural difference from every prior replay (`replay.py` picks best-XV-from-scratch each gameweek independently, by design) — Phase 7 evolves one persistent squad through real transfer decisions for the first time.

Two real bugs found and fixed during testing, not after: a sign error in the free-transfer recurrence (caught by the module's own internal LP-vs-recomputed-paid assertion, the same "verify your own accounting" discipline used since the CVaR `res.success` bug), and a crash on a currently-owned player absent from a later gameweek's universe (a postponed fixture, not a full blank gameweek) — found on the FIRST real-data run, not in synthetic tests, fixed, and regression-tested.

**Real-data validation (2022-23, GW2-38, 36 gameweeks):** myopic rolling transfers significantly beat never transferring (+4.72 pts/gw, 95% CI [+1.11,+8.25]) — confirms the whole pipeline does real work. Lookahead (horizon=4) vs myopic was not yet statistically distinguishable on one season (+0.25 pts/gw, CI [-3.25,+3.58]), but showed a real structural advantage the point-total CI didn't capture: a statistically tied score while taking zero hits (vs myopic's 7) — matching exactly the mechanism proven in a hand-derived flagship unit test (banking a free transfer to afford two simultaneous signings for a future opportunity beats greedy myopic transfers by exactly the predicted +2 points).

**Update 2026-08-15 — extended to 4 independent seasons, lookahead vs myopic CONFIRMED:** `docs/phase7_multiweek_optimizer_report.md`'s addendum. Same 4 seasons used throughout this project (2020-21, 2022-23, 2023-24, 2024-25), each with its own fresh initial squad and independent run, pooled across 147 gameweek observations, block-bootstrapped: lookahead vs myopic is now **+3.80 pts/gw, 95% CI [+2.05,+5.58]** (excludes zero), sign test p=0.0028 (87 wins/51 losses/9 ties) — resolved the same way Phase 4b's original 2-season inconclusive decision-level finding resolved at 4 seasons. Lookahead took **zero hits across all 4 seasons combined** (147 gameweeks) vs myopic's 6. No production multi-gameweek recommendation path exists yet for this to be wired into, but the underlying research question is now decisively answered: genuine multi-gameweek lookahead transfer planning beats a myopic rolling policy, and this is the evidence base for defaulting any future such feature to lookahead (horizon>=4).

## Phase 8 — Robust and stochastic optimization — DONE 2026-08-16
Full report: `docs/phase8_robust_stochastic_report.md`. Added a second, structurally different risk-aware squad optimizer alongside the earlier CVaR work (`docs/robust_captaincy_report.md`): `select_squad_mean_variance` in `src/apex_fpl/optimization/robust.py`, a Mean Absolute Deviation (MAD) linearization of Markowitz mean-variance optimization — an exact MILP (not an approximation) that penalizes dispersion symmetrically around the mean, rather than CVaR's worst-tail-only focus. 7 new tests, including a `lambda_risk=0` sanity check that must (and does) reproduce the EV squad exactly.

**Real-data result (3-way tournament, same 31-gameweek/4-season design as the CVaR replay, EV vs CVaR vs MAD run together in one script for direct comparability):** neither CVaR nor MAD shows a statistically significant mean-points improvement over EV (CVaR: -1.00, 95% CI [-4.32,+2.45]; MAD: +0.45, CI [-1.29,+2.42]) — the CVaR figure exactly reproduces the original replay's own result (same seed/design), a useful reproducibility cross-check. The genuinely informative finding: CVaR and MAD behave exactly as their different mathematical objectives predict, and differently from each other — CVaR shows real tail protection (best worst-gameweek and bottom-25%-average of the three), MAD shows none (worst of the three on both downside metrics), because MAD isn't targeting the downside specifically. A counter-intuitive but explainable result: MAD's squad has the HIGHEST dispersion of realized scores across the season despite minimizing dispersion within each gameweek's own simulated scenarios — within-week forecast uncertainty and across-season week-to-week variability are different quantities, not a contradiction.

**Decision:** both CVaR and MAD evaluated to clear NOT-PROMOTED conclusions on real multi-season data — `select_squad` (EV) remains production. Two honest negative results from a working evidence-based research process (spec Part XXVI), not two failures to "finish" the phase. CVaR's real tail-protection signal (not MAD's, which showed none) remains the more promising thread if either is revisited — more gameweeks, an alpha/lambda grid search, or combining CVaR's tail-awareness with the now-validated Phase 7 multi-gameweek transfer machinery are all left for explicit future direction.

## Phase 9 — Chips — DONE 2026-08-16
Full report: `docs/phase9_chip_valuation_report.md`. Built `src/apex_fpl/optimization/chips.py`: valuation functions for all 4 chip types (Bench Boost, Triple Captain, Free Hit, Wildcard), all reusing existing machinery rather than new forecasting logic — Wildcard specifically reuses the Phase 7 multi-gameweek `transfers.py` optimizer, since (unlike the other 3, whose value is confined to the single play-gameweek) a wildcard's squad persists afterward, so its true value must include future gameweeks. The option-value question ("does patience pay off, or should you play as soon as it looks decent?") is answered with a real, well-established optimal-stopping rule — the classical 1/e "secretary problem" rule — Monte Carlo-verified in tests to actually achieve close to its ~36.8% theoretical success rate, not just assumed to work.

**Real-data demo (2022-23, 36 gameweeks):** Triple Captain gives the expected textbook result — the stopping rule (5.67 pts) clearly beats naively playing at the first opportunity (3.85 pts), though it falls short of the unknowable hindsight-optimal (7.37 pts). Bench Boost gives the opposite, equally honest result: the true best week (GW2) fell INSIDE the rule's own mandatory observation window (the first 13 of 36 gameweeks, which the rule can never select from by construction, since that phase exists only to calibrate a threshold) — so the rule fell through to a forced last-resort pick and underperformed the naive policy. This is a real, understood limitation of the classical secretary-problem's random-order assumption when applied to one real, structured FPL season (fixture difficulty and squad freshness aren't actually shuffled at random) — reported plainly, not smoothed over, consistent with how this project has handled every other result that didn't come out as hoped (`docs/phase6_joint_simulation_report.md`, `docs/phase8_robust_stochastic_report.md`).

Free Hit (mean value 2.75 across the season) and Wildcard (mean 5.70 on an 8-gameweek sample) both produce sensible, well-ordered values against a real, evolving squad trajectory (the same validated Phase 7 lookahead policy). As with Phase 7 and 8, there's no existing production chip-recommendation path for this to be wired into or promoted against — this phase's deliverable is the validated valuation + stopping-rule machinery itself, demonstrated honestly including a real case where the "smart" policy lost. Multi-season validation of the stopping-rule finding, an FPL-structure-aware (non-uniformly-random) stopping rule, and joint chip+transfer planning are all left for explicit future direction.

## Phase 10 — Ownership and rank simulator — DONE 2026-08-16
Full report: `docs/phase10_field_simulation_report.md`. Built `src/apex_fpl/field/ownership.py` (real per-player ownership from `merged_gw.csv`'s previously-unused `selected` column, converted to a fraction via a total-manager estimate calibrated against `players_raw.csv`'s `selected_by_percent` — cross-checked by hand against 4 independent high-ownership 2022-23 players, converging to within ~1%, a real calibration not a fabricated round number) and `src/apex_fpl/simulation/field.py` (a field Monte Carlo: synthetic rival squads sampled by real ownership share, each rival's score computed by reusing the SAME per-scenario samples already drawn for the user's own squad — correctly correlating user and field within each simulated world rather than treating them as independent distributions). 10 new tests, 153/153 project-wide.

**Real-data demo (2022-23 GW20, 2,000 synthetic rivals):** the field's mean simulated score (40.70) is independently cross-checked by a naive ownership-weighted estimate computed via an entirely different mechanism (40.00, ~1.7% apart) — a genuine internal consistency signal, not a coincidence. The user's EV-optimal squad (mean 50.97) beats the field on average (mean percentile 0.780), the expected direction given fresh current-week information vs. a field average reflecting many managers' stale prior decisions.

**Honest, explicitly unresolved limitation:** there is no real average-score or rank-distribution ground truth anywhere in this historical archive to validate the field simulation's ABSOLUTE scale against — the internal cross-check confirms coherence, not external accuracy, and this is stated plainly rather than implied to be already solved. As with Phases 7 and 9, no production rank-recommendation path exists yet for this to be wired into or promoted against; this phase's deliverable is the validated capability itself. External validation (if a real source can be found), multi-gameweek demonstration, a genuine effective-ownership model (blocked on real captaincy-rate data this project doesn't have), and relaxing the budget/correlation simplifications are all left for explicit future direction.

## Phase 11 — Decision-focused research — DONE 2026-08-16
Full report: `docs/phase11_decision_focused_report.md`. A full differentiable-optimization implementation (SPO+ or similar, backpropagating through the squad-selection MILP) was judged too large an undertaking for this pass; built a smaller, well-understood, genuinely decision-focused technique instead: `src/apex_fpl/models/decision_focused.py` shrinks each player's EP toward their position's median, with the shrinkage strength TUNED to directly maximize realized squad points (not prediction loss) on 2021-22 (the project's standing tuning season). 5 new tests, including a constructed check that tuning correctly picks shrinkage=1.0 (no-op) when predictions are already perfect and shrinkage<1.0 when a player is a persistent overestimate.

**Real-data result:** tuned shrinkage=0.3 on 8 tuning gameweeks, evaluated on 31 held-out gameweeks across the same 4 independent seasons used throughout this project. Track B (shrunk EP) vs Track A (raw EP): -0.90 pts/gw, 95% CI [-2.45,+0.39] — not significant, and only 6 of 31 gameweeks even had a different resulting decision (2 better, 4 worse), consistent with the tuned value having overfit to a small 8-gameweek sample. **The more important finding:** Track B decisively fails spec Part XXVII's own joint "without sacrificing calibration" requirement — its aggregate predicted-EP/actual-points ratio collapsed to 0.375 (from Track A's 0.930), because a decision-regret-only tuning objective is structurally blind to calibration damage that doesn't change which players fill a position's fixed quota. Track C (a 50/50 hybrid) is a safer middle ground (decision-regret CI centered near zero, calibration damage roughly halved) but still not a positive result. Neither promoted — `select_squad`'s raw-EP pipeline remains production. A genuine, general methodological lesson surfaced (decision-regret-only tuning can silently wreck calibration), consistent with spec Part XXVI's expectation that some spec-listed techniques are honestly rejected by the evidence, which is a successful outcome of the research process, not a failure to finish.

## Phase 12 — Production system — DONE 2026-08-16 (pipeline built and dry-run validated; scheduling left as an open decision)
Full report: `docs/phase12_production_system_report.md`. Every research phase (2-11) ran against the historical Vaastav archive — none had ever touched the LIVE 2026/27 Bronze/Silver data the daily snapshot job has been capturing since 2026-08-14. Built `src/apex_fpl/serving/live_data.py` (a genuine live-data adapter — found and fixed two real integration facts: the canonical CSVs are append-only across daily snapshots, and live `element_type_id` maps to "GKP" while every optimizer in this project is keyed on the historical archive's "GK" convention) and `scripts/run_production_recommendation.py` (full orchestration using ONLY the confirmed champions — explicitly not any not-promoted challenger).

**A real structural problem surfaced while building this, not assumed away:** no model needing current-season history (team strength, minutes, attacking allocation) can have any at GW1 of a brand-new season. Team model: solved via a historical-fixture fallback (2024-25 fixtures combined with the existing 380-day decay), with a stated limitation that 2025/26 isn't yet in the archive so this prior is staler than the mechanism was designed for. Minutes: solved with a genuinely validated cold-start model (`src/apex_fpl/models/minutes/cold_start.py`, price-based isotonic regression) — checked by hand first that season-opening price predicts GW1 starter likelihood (a real, consistent pattern across all 4 independent seasons), then validated via leave-one-season-out CV, beating a flat baseline on held-out log loss in all 4 folds. Attacking allocation: NOT solved — no validated cold-start equivalent exists yet (blocked on player-ID reconciliation between the live API and the historical archive, the same problem Phase 10 hit with ownership data), so the production script uses an explicitly UNVALIDATED price-weighted fallback and tags every recommendation with that caveat rather than hiding it.

**Dry run** against real live 2026/27 GW1 Bronze data produced a legal squad (587 players, 15,000 simulated scenarios, correct 2/5/5/3 quotas) with Haaland captained — genuinely un-scoreable since the season hasn't started, but a real integration test the research phases could never have run. 8+4 new tests, 166/166 project-wide.

**Deliberately NOT done**: extending the existing live launchd automation (`com.apexfpl.snapshot.plist`) to schedule this script — a real, persistent, system-level, unattended change hitting the live FPL API on its own, left as an explicit decision point for the user rather than taken unilaterally, consistent with this project's own operating guidance on hard-to-reverse or shared-state-affecting actions.

## Governing constraints across every phase
- Lockbox (Dataset C) is never touched outside `fpl evaluate-lockbox`, logged per Part LXII.
- Prospective 2026/27 forecasts are frozen pre-deadline and never edited after outcomes are known (Part LXIII).
- A challenger only replaces a champion under the promotion criteria in Part LXI — improvement must be stable, calibration-preserving, and operationally justified, not just numerically better on one split.
- Complexity is added only when ablation shows repeatable value (Part LX's stopping rule); this plan explicitly expects some spec-listed techniques (e.g. decision-focused learning, robust optimization) to be rejected as challengers if the evidence doesn't support them, and that outcome is a successful use of the research process, not a failure to "finish" the spec.

## Out-of-order work — captaincy risk & robust optimization (2026-08-15)
Done ahead of the Phase 6/7 sequence at explicit user direction, pulling forward pieces of Phase 28 (captaincy) and Phase 26 (robust optimization). Full report: `docs/robust_captaincy_report.md`.

**Captaincy risk** (`src/apex_fpl/optimization/captaincy.py`): distributional metrics + 3 selection modes (EV/risk-averse/ceiling) + joint captain-vice fallback simulation, all computed from real Monte Carlo samples. Working correctly (verified via constructed divergence tests); effective ownership and rank-gain are explicitly not computed since no ownership/field model exists yet.

**Robust (CVaR) optimization** (`src/apex_fpl/optimization/robust.py`): exact Rockafellar-Uryasev MILP formulation, mathematically proven to dominate the EV squad on its own training scenarios. An initial single-seed real-data test found no out-of-sample downside advantage; a 6-trial multi-seed scenario-count sweep superseded that (all 6 trials favored CVaR on downside metrics, small mean cost, convergence by n>=800). **Final update 2026-08-15 — the multi-gameweek downside replay is done (`docs/robust_captaincy_report.md`): NOT PROMOTED.** 31 real gameweeks across the 4 independent seasons, mean-points 95% CI [-4.32,+2.45] (includes zero) — does not clear this project's promotion bar. The evidence is genuinely mixed, not a clean rejection: CVaR's worst single gameweek (33) clearly beat EV's worst (23), and CVaR notably outscored EV in 4 of EV's 5 worst gameweeks — a real disaster-recovery signal — but simple per-gameweek win/loss actually favored EV (12-16, not significant) and the tail-average edge was small on only 8 tail observations. Two real engineering bugs were found and fixed en route: unbounded MILP solves occasionally took 15+ minutes (early-season data, a known branch-and-bound phenomenon — added a `time_limit` parameter), and scipy's `res.success` being `True` only when optimality is *proven* meant a time-limited-but-feasible solution was being wrongly treated as failure (fixed to check solver status correctly). `champion_unfit`-derived EV selection remains the production squad optimizer. More gameweeks or unbounded solve time are the concrete paths to a sharper answer, both left for explicit future direction.

## What this plan deliberately does not do yet
It does not pre-commit to specific model families winning any tournament, does not assume which data sources will ultimately be available, and does not promise a completion date — the spec is explicit that this is a continuous research program, not a project with a final deliverable date. Each phase's exit criterion is empirical (a specific test passes, a specific artifact exists and is falsifiable) rather than calendar-based.
